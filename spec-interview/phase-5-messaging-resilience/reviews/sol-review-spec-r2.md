1. **High — §7 FR-001/003; §14 AC-004/038: an initial online send can disappear.** Persistence is required only after a transient failure. Closing the tab before the request settles can lose both the message and its key, violating R1-q2 A. The current key lives in a React ref, and dispatch uses plain fetch. Evidence: [message-composer.tsx:145](/E:/projects/virtual-office/src/components/messaging/message-composer.tsx:145), [messaging-api.ts:131](/E:/projects/virtual-office/src/lib/messaging-api.ts:131). **Fix:** require durable storage of every eligible send before dispatch or composer clearing; add E2E coverage for closing the sending tab before server confirmation.

2. **High — §7 FR-004/007; BR-005/007; AC-006/010/038: “not currently in flight” does not mean unsent.** A committed request whose response is lost becomes pending and cancellable, although B may already have received it. It can also become “expirada” despite already being stored. Evidence: [SPEC.md:178](/E:/projects/virtual-office/spec-interview/phase-5-messaging-resilience/SPEC.md:178), [create/route.ts:332](/E:/projects/virtual-office/src/app/api/messages/create/route.ts:332). **Fix:** distinguish confirmed-unsent from unknown-outcome attempts. Reconcile unknown outcomes before offering cancellation or declaring expiry; an existing committed message must resolve as delivered. Test response loss followed by cancel and by expiry.

3. **High — §3 success metrics; FR-002; AC-002: unconditional 10-second delivery contradicts rate limiting.** Create permits 30 requests per 60 seconds, and replay requests consume quota before idempotency lookup. A large queue or exhausted quota cannot satisfy the deadline while honoring FR-006. Evidence: [rate-limit.ts:10](/E:/projects/virtual-office/src/lib/auth/rate-limit.ts:10), [create/route.ts:272](/E:/projects/virtual-office/src/app/api/messages/create/route.ts:272), state.md R1-q2 C and R2-q4 A. **Fix:** state the queue-size, available-quota, and latency conditions for the delivery target; explicitly address server-enforced waits. Obtain owner confirmation for the qualification instead of silently replacing delivery with “retry starts.”

4. **High — §6 J2; AC-004; §5 exclusions: fully offline reload requires excluded capabilities.** IndexedDB persistence does not make the Next.js document, JavaScript, or profile bootstrap available offline. The application has server-side authentication in its navigation path and no specified offline shell. Evidence: [proxy.ts:45](/E:/projects/virtual-office/src/proxy.ts:45), [CompanyContext.tsx:187](/E:/projects/virtual-office/src/contexts/CompanyContext.tsx:187), [next.config.ts:3](/E:/projects/virtual-office/next.config.ts:3). R1-q3 promises persistence through reload/close, not successful offline application loading. **Fix:** make AC-004 prove persistence through a failed offline reload and recovery when the app can load again, or obtain approval for offline app loading.

5. **High — FR-003/004; BR-003/007; AC-005/006: the tests cannot prove exclusive ownership or recovery.** Existing server uniqueness lets two simultaneous senders pass AC-005’s one-row assertion. AC-006 does not exercise cancel versus claim, and nothing covers abandoned persistent “in-flight” state or a stalled owner. Evidence: [idempotency migration:61](/E:/projects/virtual-office/supabase/migrations/20261005000414_messages_client_message_id_idempotency.sql:61), state.md R2-q7. **Fix:** require atomic claim/cancel transitions and recoverable ownership. Assert concurrent HTTP attempts, test cancellation at the claim boundary, close the owning tab, and hold a real create request while another tab attempts recovery.

6. **High — FR-009/010; BR-001/008; AC-012/013: account switching and logout are tested only after settling.** A queued callback can resume after browser cookies switch to C. Create derives the sender from those cookies, so C’s membership in the same conversation can authorize A’s text as C. Deleting IndexedDB alone also does not stop another tab’s worker or late completion. Evidence: [messaging-api.ts:131](/E:/projects/virtual-office/src/lib/messaging-api.ts:131), [create/route.ts:301](/E:/projects/virtual-office/src/app/api/messages/create/route.ts:301). **Fix:** specify identity-generation fencing across claims, dispatches, and completions, including explicit logout. Add paused-dispatch account-switch and in-flight logout E2Es; verify the existing Presence logout sequence with pending messages.

7. **High — FR-016; BR-009; §12; AC-019: join-time RLS does not ensure current-members-only typing.** Supabase caches channel authorization; removing membership does not immediately remove an existing subscriber’s access. AC-019 tests only someone who was already a non-member. Evidence: [Supabase authorization documentation](https://supabase.com/docs/guides/realtime/authorization#updating-rls-policies), [useConversationPresence.ts:94](/E:/projects/virtual-office/src/hooks/useConversationPresence.ts:94). **Fix:** require a revocation-aware authorization mechanism and membership-scoped send/receive permissions. Test an already-joined member’s removal, authenticated outsiders, anon clients, and public/private topic attempts using real Realtime.

8. **High — FR-021/022; §9; AC-024/025/038: mention creation and replay have no atomic contract.** The existing message INSERT contains no mention records; notifications run from that INSERT. Adding mention rows afterward can lose room notifications or leave a committed message without its mentions. Existing composition comparison also excludes mentions. Evidence: [useMessageSubscription.ts:48](/E:/projects/virtual-office/src/hooks/realtime/useMessageSubscription.ts:48), [use-message-notifications.ts:60](/E:/projects/virtual-office/src/hooks/ui/use-message-notifications.ts:60), [create/route.ts:78](/E:/projects/virtual-office/src/app/api/messages/create/route.ts:78). **Fix:** require atomic message/mention persistence, immutable mention identity on replay, and authoritative enrichment before notification decisions. Test mention-write failure, changed mention IDs under one key, and a hidden recipient viewing another conversation. Add direct-table anon/non-member read and unauthorized-write checks.

9. **High — BR-011; FR-022; AC-025/026: cross-tab viewing suppression can fail while deduplication succeeds.** Each tab decides locally, then races for a Web Lock. A hidden tab winning first notifies even when another visible tab is viewing the conversation. The existing two-tab test uses two background tabs. Evidence: [use-message-notifications.ts:114](/E:/projects/virtual-office/src/hooks/ui/use-message-notifications.ts:114), [desktop-notifications.ts:189](/E:/projects/virtual-office/src/lib/messaging/desktop-notifications.ts:189), [notification E2E:316](/E:/projects/virtual-office/__tests__/api/playwright/messaging-desktop-notifications.spec.ts:316). **Fix:** define browser-wide viewing eligibility before notification claiming. Add visible-plus-hidden tests with the hidden tab receiving first, alongside once-across-tabs mention tests.

10. **Medium — BR-004/005; FR-005; AC-008: retrying a key-reuse rejection cannot recover.** `CLIENT_MESSAGE_ID_REUSED` is definitive, but every manual attempt must reuse the same key and unchanged composition; the route returns 409 again. Evidence: [create/route.ts:100](/E:/projects/virtual-office/src/app/api/messages/create/route.ts:100). **Fix:** distinguish recoverable failures from terminal composition conflicts. Specify an actionable discard/recompose path for 409 rather than promising an unchanged retry that cannot succeed.

11. **Medium — BR-005; FR-009; AC-012: HTTP 401 is not reliable proof of session expiry.** `requireAuthUser` maps almost every `getUser()` error to 401, including temporary Auth failures. The client discards status/code and throws only the response text. Server-side revocation also does not itself guarantee immediate JWT rejection or a browser event. Evidence: [session.ts:120](/E:/projects/virtual-office/src/lib/auth/session.ts:120), [messaging-api.ts:151](/E:/projects/virtual-office/src/lib/messaging-api.ts:151), [Supabase session documentation](https://supabase.com/docs/guides/auth/sessions#how-to-ensure-an-access-token-jwt-cannot-be-used-after-a-user-signs-out). **Fix:** require typed outcomes, separate temporary Auth unavailability from verified session termination, and define the observable revocation boundary used by AC-012.

12. **Medium — FR-010; AC-013: cancellation can still trigger login navigation.** Both sign-out callers redirect after a normally resolved `signOut()`. Adding confirmation inside that function and returning on Cancelar would leave the session intact but redirect anyway. Evidence: [dashboard-header.tsx:30](/E:/projects/virtual-office/src/components/shell/dashboard-header.tsx:30), [enhanced-user-menu.tsx:28](/E:/projects/virtual-office/src/components/shell/enhanced-user-menu.tsx:28). **Fix:** require Cancelar to produce no logout request, success notice, or navigation at every entry point; test both callers and preserve the Presence fence ordering on confirmation.

13. **Medium — §2; FR-012/013; AC-015/016: failure and recovery semantics are incomplete.** The SPEC calls the conversation channel incapable of reconnecting, but the resolved SDK already retries errored/timed-out channels. The current exposed status covers only the message channel, while AC-015 drops both channels together and cannot detect that limitation. Evidence: [SDK channel.js:46](/E:/projects/virtual-office/node_modules/@supabase/phoenix/assets/js/phoenix/channel.js:46), [MessagingContext.tsx:251](/E:/projects/virtual-office/src/contexts/messaging/MessagingContext.tsx:251). **Fix:** describe the missing application recovery for terminal closures accurately; define health across the required streams, including typing recovery. Test channels independently and polling/Realtime response overlap, asserting no new polling starts after recovery and no duplicated or degraded messages.

14. **Medium — FR-024/025; BR-013; §12; AC-028/029: benign events do not prove redaction, abuse resistance, or nonblocking delivery.** Payload/batch limits do not prevent authenticated log flooding or PII embedded in allowed string fields. AC-029 tests errors, not slow requests. “Unauthenticated requests … write nothing” also conflicts with the shared error helper’s unconditional logging. Evidence: [server-error.ts:84](/E:/projects/virtual-office/src/lib/api/server-error.ts:84), state.md R2-q2 and confirmation. **Fix:** require closed event/reason enums, validated numeric fields, trusted version metadata, request-rate limits, bounded client buffering, and no awaiting metrics on messaging paths. Test malicious payloads and held metrics requests. Narrow “nothing logged” to messaging metric payloads.

15. **Medium — FR-018; AC-021: unread badges alone do not validate read-state synchronization.** The AC checks only that three unread become zero; it never asserts receipt status, reader details, or partial reading across devices. Evidence: [SPEC.md:239](/E:/projects/virtual-office/spec-interview/phase-5-messaging-resilience/SPEC.md:239), state.md R1-q9 A. **Fix:** add partial-read cross-device coverage and assert the sender’s receipt summary/details agree with the authoritative rows on both sender sessions. Define observable deadlines for “live” ACs instead of leaving eventual success unbounded.

16. **Medium — FR-020/021; BR-010; AC-024: self-mention exclusion is invented scope.** The answers require conversation-member selection and prohibit notifications for one’s own messages; they do not prohibit selecting or recording oneself. Evidence: [state.md:128](/E:/projects/virtual-office/spec-interview/phase-5-messaging-resilience/state.md:128), [state.md:144](/E:/projects/virtual-office/spec-interview/phase-5-messaging-resilience/state.md:144). **Fix:** remove self-exclusion from selection/storage while retaining own-message notification suppression, or obtain an explicit owner decision.
