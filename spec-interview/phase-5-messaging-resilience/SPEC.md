# SPEC: Phase 5 — Messaging Resilience

Goal: In the production messaging drawer, no message a user sends is lost or duplicated across network and Realtime outages, reloads, several tabs, account changes, and several devices; typing, unread/read state, and @mention notifications stay live and correct; and messaging health is observable through redacted logs — without regressing existing messaging.

Status: Final v4 — revised after adversarial reviews r2–r4 (`reviews/sol-review-spec-r2.md` … `r4.md`); r4 fixes applied without a fifth review by owner decision D7 (2026-10-06). Approved by the owner 2026-10-06 (native question UI: "Aprovada"). Interview rounds 1–2, confirmation, and owner decisions D1–D6 recorded in `state.md` (Verdict: Ready).

## 1. Summary

The Virtual Office messaging drawer (`MessagingDrawer` → `MessageFeed` → `MessageComposer` / `MessageItem`, state in `MessagingContext`, data in `useMessages` / `useConversations`, Realtime in `useMessageSubscription` / `useConversationRealtime`, typing in `useConversationPresence`) was completed for timeline features in Phase 4. Phase 4 also delivered a failed send that keeps text/reply/files with a single-message retry (`clientMessageId` idempotency in `POST /api/messages/create`, stored in `messages.client_message_id`), a Realtime catch-up after reconnect, and opt-in desktop notifications for DM/group messages. This phase adds: a durable per-user outbox for text messages with server-fenced attempt generations and safe cross-tab and cross-account behavior; a connection banner; application-level recovery and health for every messaging Realtime stream with polling fallback; a reliable, named, members-only typing indicator; live cross-device unread/read sync; @mentions with desktop notifications (including rooms); messaging health metrics as redacted server logs; and two Phase 4 database follow-ups plus restoring the open conversation after reload.

## 2. Problem statement

Workspace members using the chat on unstable networks or sleeping laptops lose work and trust: a send that fails must be retried by hand, a reload or closed tab discards it (the idempotency key lives only in component memory), and nothing tells the user the chat is disconnected. Optimistic messages are matched to stored ones by guessing from content and time. Realtime recovery is incomplete: the SDK retries errored/timed-out channels and the conversation-list stream invalidates the list after its own rejoins, but the application exposes health only for the messages channel, does not recover terminal closures of the conversation-list channel, has no aggregate health, and has no polling fallback, so new messages and unread counts can silently stop updating. The typing indicator disappears after ~4 s of continuous typing and is broadcast on a public channel. Reading on one device leaves stale unread badges on the user's other devices. Nobody can mention someone, so room conversations (which never notify) cannot reach a specific person. Nobody can tell in production whether messaging is healthy.

## 3. Goals and success metrics

### Goals
- G1: A text message the user sends is never silently lost: it is delivered, pending, or visibly failed with an action.
- G2: No message is ever stored or shown twice because of automatic resends, several tabs, lost or late responses, or account changes; a message is never stored under a different sender.
- G3: Messaging recovers from network and Realtime outages without user action and keeps updating through polling while Realtime is down.
- G4: Typing indicators are reliable, named, and visible only to conversation members.
- G5: Unread/read state and own sent messages stay in sync across the same user's tabs and devices (≤ 5 s while connectivity is healthy).
- G6: A user can @mention conversation members, and the mentioned person is notified on the desktop, including in rooms.
- G7: Messaging health (latency, delivery, connection) is observable in technical logs without exposing content.
- G8: No existing messaging behavior regresses; every database change reaches the online target in a controlled, verified way at phase end.

### Success metrics
- With ≤ 10 pending messages and create quota available, all pending messages are delivered within 10 s after connectivity returns, without any click, in their original order, each exactly once; with more, delivery continues automatically within the server rate limit (D1).
- With Realtime down and HTTP working, other members' new messages appear within 45 s of the outage start, and within 15 s (plus request time) of being sent once polling is active.
- With healthy connectivity and Realtime, cross-device/tab sync of unread counts, read state, and own sent messages within 5 s (D4); during a Realtime outage the polling deadlines above apply.
- Each flow is covered by a passing Playwright E2E test (two accounts, and two tabs / two devices where relevant) that passed 3 consecutive runs in Chrome and Edge [amended by owner decision D16, 2026-10-10: one browser only — Chrome; no Edge run, no Firefox verification].
- The existing messaging regression E2E suite passes after each slice.
- Every migration of the phase is applied to the online target `vhabpcoyypobgasacsko` at phase end with explicit owner authorization, catalog readback, and a runtime smoke check.
- Owner final test (new app against the online database) accepts the phase.

## 5. Scope

### In scope
- Durable outbox (IndexedDB, per application user, per browser) for text messages and replies, written before dispatch; item states; cancel; per-conversation ordered automatic drain across tabs; claim leases and recovery; server-fenced attempts; identity fencing; rejection, rate-limit, and 24 h expiry handling; session-end and sign-out rules; sending blocked with a clear message when durable storage is unavailable (D5).
- Server support on create: sender fencing; attempt-generation fencing; key-based correlation (`clientMessageId` exposed to the sender in every message representation); insertion quota charged only for a winning insertion, plus an independent request budget for all create attempts and a separate budget for fence/lookup calls; mentions persisted atomically with the message and compared against the original composition on replay; a fence/lookup call by `clientMessageId` that never creates a message.
- Connection banner in the drawer.
- Application-level recovery, health, and catch-up for every messaging Realtime stream (messages/receipts/reactions, conversation list, typing of the open conversation).
- Polling fallback after > 30 s of a required stream outage, while the tab is visible.
- Typing indicator: continuous display, names, DM/group/room, private members-only channel, own sessions excluded, expiry.
- Cross-device/tab sync of unread counters, read state, and own sent messages.
- @mentions: autocomplete, highlighted mention, server-validated atomic mention records, desktop notification (DM, group, room, thread reply) authorized at emission time with browser-wide viewing suppression, feed highlight.
- Messaging metrics as redacted structured server logs via an authenticated, rate-limited, size-bounded application route.
- Phase 4 follow-ups: membership check inside `mark_conversation_read`; `get_unread_counts` not executable by `anon`; restore the open conversation after page reload.

### Out of scope
- Loading the application while offline (service worker / offline app shell) (D2).
- Queuing attachments or voice notes (they keep the Phase 4 behavior).
- Editing a pending message (cancel and rewrite instead).
- Web Push / notifications with the browser or tab closed; cross-device notification suppression or dismissal.
- `@todos` / `@here`; self-mentions; a separate mention-only notification preference; scrolling to the message on notification click.
- Draft persistence; live sync of stars.
- Usage/engagement metrics; a metrics UI or external analytics service.
- Immediate revocation of typing signals for a tampered client of a removed member (accepted residual risk ≤ access-token lifetime, D3).
- Safari and mobile browsers; drawer layout below ~400 px.
- Other Phase 4 follow-ups: pending-upload cap, toaster covering the composer, pin no-op/English copy, orphan storage objects, "Favoritas" discoverability.
- Deploying the application (owner action).

## 6. User journeys

- J1 Offline send: A loses internet and keeps writing; each message appears as pending; the banner says "Sem conexão — mensagens serão enviadas quando voltar". Internet returns; with ≤ 10 pending and quota available, every pending message is delivered within 10 s in order and B sees each once; with more, delivery continues within the rate limit (D1).
- J2 Reload/close: A has pending messages and reloads while offline (the browser shows its normal offline error) or closes the tab. When the page loads again with internet, the pending messages are there and are sent.
- J3 Two tabs: A's pending message shows in both tabs as one item; only one tab sends a conversation's messages at a time; if that tab closes or hangs mid-send, the other finishes them once; cancelling a waiting message in either tab removes it from both.
- J4 Rejection: A's pending message targets a room A has since lost access to; it becomes a visible failure with the text kept and "Tentar de novo" / "Apagar"; later pending messages for that room wait; other conversations still deliver.
- J5 Sign-out: A clicks Sair with 2 unsent messages; a dialog warns that leaving deletes them; Cancelar leaves A exactly where A was; Sair mesmo signs A out.
- J6 Shared browser: A's session ends without Sair; C signs in on the same browser; C never sees A's messages and nothing is sent as C; when A signs in again, A's messages are sent as A.
- J7 Realtime outage: after 5 s the banner shows "Reconectando…"; after 30 s the open conversation and the list update every 15 s; when Realtime returns, polling stops and the banner disappears.
- J8 Typing: B types continuously in a group; A sees "Bruno está digitando…" the whole time; it disappears ≤ 5 s after B stops or leaves.
- J9 Two devices: A reads part of conversation X on the laptop; within 5 s the desktop's badge and read state for X match.
- J10 Mention: A types "@" in a room chat and picks Bruno; Bruno's tab is hidden; Bruno gets "Ana mencionou você em <sala>" with the full text; clicking opens the room; the message is highlighted for Bruno.
- J11 Reload restore: A reloads with the drawer open on conversation X; the drawer reopens on X.

If the durable write fails, nothing is dispatched (FR-033). The item shows in the feed as pending while not confirmed by the server. | Must | AC-001, AC-003, AC-040 |
| FR-002 | Pending items are sent automatically when connectivity returns (browser online, Realtime recovery, or periodic retry), per conversation in creation order, always with their own `clientMessageId`. With ≤ 10 pending and quota available, all are delivered within 10 s of connectivity returning; with more, delivery continues within the rate limit. A confirmed item becomes the normal sent message and leaves the outbox. | Must | AC-002, AC-009, AC-038 |
| FR-003 | The outbox survives reload and tab close. Reloading while offline shows the browser's normal offline error; when the app loads again, the pending items are shown and sent. Items of the current user appear in every tab of the same browser. | Must | AC-004 |
| FR-004 | Cross-tab ordering and ownership: the outbox order is shared by all tabs; per conversation, only the oldest unresolved item is eligible, and at most one tab holds the conversation's drain claim at a time (atomic claim). A claim is a lease: it ends when its tab closes or crashes, or when its holder exceeds the attempt deadline (request timeout 30 s; lease 45 s), and another tab then resumes after fencing (FR-006). When connectivity returns, an attempt that started before or during the outage is superseded immediately (fenced and redispatched under a new generation by whichever tab drains), so a hung holder never delays the D1 deadline. Across all tabs, no two create requests of the same conversation's outbox are in progress at once. | Must | AC-005, AC-041 |
| FR-005 | Cancel: an item can be cancelled from any tab only if it is known not to be stored and no earlier attempt can still commit (never dispatched, last attempt definitively rejected, or fenced as not stored) and it is not claimed; the cancel is an atomic transition against claims — a cancelled item is never dispatched afterwards; a dispatched item shows "enviando" without cancel. | Must | AC-006 |
| FR-006 | Attempt fencing: each dispatch is an attempt of the item's `clientMessageId`. Every create and fence request carries the item's attempt generation (monotonic per key). The server accepts a create only if its generation is the current one for that (sender, conversation, key) at the moment of commit, and a fence with generation g atomically either returns the stored message (item resolves as delivered) or makes every generation below g unable to commit — including requests still in the network that have not reached the server; a fence or create with a generation older than the server's current one is rejected. When an attempt ends without a usable response (network error, timeout, tab closed, lease expired, superseded, HTTP 5xx), the item is unknown; before any cancel, expiry, takeover, or new dispatch, the app fences it. The fence never creates a message. | Must | AC-038, AC-042, AC-045 |
| FR-007 | A definitive rejection (BR-005) stops automatic attempts for that item; it shows as failed with its text and actions "Tentar de novo" and "Apagar"; later items of the same conversation wait until it is resolved; other conversations are unaffected. For `CLIENT_MESSAGE_ID_REUSED`, "Tentar de novo" sends the same content under a new `clientMessageId`. | Must | AC-007, AC-008, AC-043, AC-046 |
| FR-008 | A rate-limit rejection is transient: the item stays pending and is retried automatically, preserving order and without duplicates. The insertion quota is charged only for a winning insertion (including among concurrent requests for the same key); replays that return an already-stored message do not consume it (D1). Independently, every create request (including replays, validation failures, and quota losers) consumes a per-user request budget, and fence/lookup calls consume their own per-user budget; exceeding any budget is a transient rate limit. | Must | AC-009 |
| FR-009 | An item not stored 24 h after the user pressed send is never sent automatically: once fenced as not stored, it shows as failed "expirada" with "Tentar de novo" and "Apagar"; an unknown item found stored resolves as delivered, never as expired. "Tentar de novo" on an expired item keeps the key and the original send time (for metrics) and starts a new 24 h delivery window, within which the normal transient/unknown rules apply. | Must | AC-010, AC-042 |
| FR-010 | Attachments/voice are never queued. A file whose upload fails offline keeps the existing per-file error and retry (send stays disabled until uploads finish); a message whose uploads succeeded but whose create request fails keeps the Phase 4 composer failure and "Tentar de novo". | Must | AC-011 |
| FR-011 | Identity fencing: each item belongs to an application user (`users.id`). Before every dispatch and fence call the app checks that the authenticated user equals the item's owner; every dispatch carries the expected sender, and the create and fence routes reject (without storing or fencing) a request whose authenticated user differs. When the authenticated user changes or signs out in any tab, all drains in all tabs stop; create, fence, and lookup responses that arrive afterwards are discarded: they never add content to another user's view, never resurrect deleted items, and never change a newer claim. Under the same identity, a response whose attempt generation is older than the item's current generation, or for an item already cancelled/deleted, is likewise ignored. | Must | AC-012, AC-044, AC-047 |
| FR-012 | Session end without explicit sign-out: an item is held (not failed, not deleted) only when the client's auth state reports the session ended (signed out, or refresh rejected); a 401 while the client still holds a valid session is treated as transient. Held items drain after the same user signs in again (subject to FR-009); another user on the browser never sees, sends, or deletes them. | Must | AC-012 |
| FR-013 | When the user clicks Sair at any in-app sign-out entry point with N > 0 unsent items, a dialog shows "Você tem N mensagens não enviadas. Sair apaga essas mensagens." with "Sair mesmo" and "Cancelar". Cancelar produces no logout request, success notice, or navigation. Sair mesmo stops drains in all tabs, deletes that user's outbox, and runs the existing sign-out (including the Presence logout sequence unchanged). With N = 0 sign-out is unchanged. | Must | AC-013 |
| FR-014 | Banner: "Sem conexão — mensagens serão enviadas quando voltar" as soon as the browser reports offline; "Reconectando…" when any required messaging Realtime stream (messages/receipts/reactions, conversation list) has been unhealthy for more than 5 s while the browser is online; it disappears by itself once all are healthy. | Must | AC-014 |
| FR-015 | Every messaging Realtime stream (messages/receipts/reactions, conversation list, typing of the open conversation) has application-level health and recovery: after an error, timeout, or terminal closure it rejoins without user action using exponential backoff with a capped delay (in addition to the SDK's own retries); on recovery the messages and conversation-list streams trigger a catch-up refetch of the open feed and the list; the typing stream rejoins. | Must | AC-015 |

| BR-001 | The outbox belongs to one application user (`users.id`) on one browser; it is never shown, dispatched, fenced, or deleted while another user is authenticated, and the server never stores or fences an item under a sender other than its owner. | R1-q3 A, R1-q16 A, R2-q5 A; reviews r2 #6, r3 #4 |
| BR-002 | Only text messages and replies without attachments/voice are queued. | R1-q4 A |
| BR-003 | Per conversation, items are sent in creation order with at most one create request in progress across all tabs; a failed (definitive or expired) item blocks later items of that conversation until the user retries or deletes it. | BR-004 | Each item gets a stable `clientMessageId` when the user presses send; every attempt reuses it (except the `CLIENT_MESSAGE_ID_REUSED` retry, FR-007); the server stores at most one message per (sender, conversation, `clientMessageId`), and a fenced attempt can never commit. | R1-q2 B, R1-q16 B; review r3 #1 |
| BR-005 | Outcome classes: transient = browser offline before dispatch, HTTP 429, HTTP 401 while the client session is valid → retry automatically; unknown = network error/timeout/no response after dispatch, lease expiry, HTTP 5xx → fence (FR-006); session-ended = client auth reports signed out / refresh rejected → hold (FR-012); definitive = 403 `NOT_PARTICIPANT` (incl. a missing conversation), 400 (e.g. `INVALID_REPLY_TARGET`), 413 `CONTENT_TOO_LARGE`, 409 `CLIENT_MESSAGE_ID_REUSED`, sender mismatch, and any other 4xx except 401/429 → failed, no automatic retry; a stale-generation rejection only means a newer attempt exists and is ignored (FR-011). | R1-q5 C, R2-q4 A, R2-q5 A; reviews r2 #2, #11 |

| BR-007 | Cancel only for items known not to be stored, with no earlier attempt able to commit, and not claimed; a cancelled item is removed in all tabs and never dispatched. | R1-q5 B, R2-q7 A; reviews r2 #2, #5, r3 #1 |
| BR-008 | An explicit user sign-out with unsent items requires confirmation; confirming deletes that user's outbox; a sign-out not initiated by the user keeps it. Cancelling has no side effect. | R2-q5 A, R2-q6 A |

## 9. Data and integrations

### Data inputs
- Composer text, reply target, and mention selections (user IDs).
- Browser connectivity events, Realtime stream status, tab visibility, Supabase auth state changes.
- Responses from `POST /api/messages/create` (status and error code) and from the fence/lookup call.

### Data outputs
- Browser IndexedDB outbox keyed by application user ID: `clientMessageId`, conversation ID, text, reply target, requested mention user IDs, pressed-send time, delivery-window start, order, state (waiting / claimed / unknown / failed + reason / expired), attempt generation, claim holder and lease expiry. Deleted per BR-007/BR-008; never shared across users.
- Database: attempt-generation state per (sender, conversation, `clientMessageId`) so a fenced or stale generation cannot commit; the original submitted composition used for replay comparison; mention records written atomically with the message; private typing-topic authorization (RLS on `realtime.messages`, `users.supabase_uid = auth.uid()::text` → `users.id` membership); `mark_conversation_read` with an internal membership check; `get_unread_counts` without `anon` EXECUTE; rate-limit buckets for all create requests and for fence/lookup calls, separate from the insertion quota.
- API: create route sender and attempt-generation fencing, winning-insert quota charging, request budget, `clientMessageId` in responses; fence/lookup route for the caller's own message only; authenticated, rate-limited, size-bounded metrics route.
- Structured metric log lines (BR-013).
- Persisted drawer state per user: open flag + active conversation ID.

### Integrations
- Supabase Postgres, Realtime (`postgres_changes`, private broadcast topics), Auth (server routes use `createSupabaseServerClient` + `auth.getUser()`).
- Browser APIs: IndexedDB, Web Locks and/or BroadcastChannel for cross-tab claims and signals, Notification API (Phase 4), Page Visibility.
- Hosting/Supabase logs as the metrics sink; no new external analytics dependency.

## 11. Edge cases and failure modes

| Case | Expected behavior |
|---|---|
| Tab closed right after pressing send, before server confirmation | Item is already in the outbox; on next load it is fenced and delivered once (AC-040). |
| Request stored but response lost | Item becomes unknown; fence finds it stored; resolves as delivered; never offered for cancel or expired (AC-038, AC-042). |
| Original create blocked before its INSERT, or still in the network, while another tab fences | The fence wins; the older generation can no longer commit; the item is resent once or cancelled/expired without a late duplicate (AC-045). |
| Stale fence arrives after a takeover | Rejected as an older generation; the newer attempt is unaffected (AC-045). |
| Hung holder when connectivity returns | Its attempt is superseded at once; D1 deadline holds (AC-041). |
| Two tabs come online together | One drain claim per conversation; only the oldest unresolved item is eligible; no overlapping create requests for that conversation; each stored and shown once, in order (AC-005). |
| Owning tab closes or hangs mid-request | Closed or lease expired: another tab fences and finishes once; while the lease is live no other tab dispatches (AC-041). |
| Cancel races a claim | Exactly one wins; a cancelled item is never dispatched; a dispatched item cannot be cancelled (AC-006). |
| Lost access before reconnect | First item fails definitively with text; later items of that conversation wait; other conversations deliver (AC-007). |
| Access regained after failure | "Tentar de novo" delivers it, then the waiting items in order (AC-008). |
| Other definitive outcomes (404, 400, 413, 422) and 5xx | Definitive → failed with text; 5xx → unknown → fence (AC-046). |
| `CLIENT_MESSAGE_ID_REUSED` | Failed; "Tentar de novo" resends the content under a new key, once (AC-043). |
| Server rate limit during drain; concurrent same-key requests | Items stay pending, retried automatically; quota charged once per stored message; replays/fences use a separate budget (AC-009). |
| Laptop asleep > 24 h | Not-stored items become "expirada"; stored ones resolve as delivered (AC-010, AC-042). |
| Offline attachment / voice | Upload failure: per-file error + retry; create failure after upload: Phase 4 composer failure; nothing in the outbox (AC-011). |
| IndexedDB unavailable or write fails | Nothing dispatched; text stays in the composer with the storage message (D5) (AC-039). |
| Identical texts sent twice; Realtime arrives before the HTTP response | One bubble per message, matched by key (AC-050). |
| Account switched while a drain is paused or a response is in flight | Drain stops; no dispatch as the new user; late responses discarded; server rejects any request whose sender differs (AC-044, AC-047). |
| Session ends without Sair; other user signs in | Other user never sees/sends A's items; A's items drain after A signs in (AC-012). |
| Temporary Auth failure (401 with valid client session) | Treated as transient; retried; not held or deleted (AC-012). |
| Sair with unsent items | Dialog; Cancelar has no side effects at any entry point; Sair mesmo stops drains everywhere and deletes the outbox; late responses do not resurrect items (AC-013, AC-047). |
| Realtime drop < 5 s | No "Reconectando…" banner (AC-014). |
| Only the conversation-list stream fails | Banner after 5 s and polling after 30 s follow its health; recovered independently (AC-015, AC-016). |
| Stale poll returns after a newer Realtime update | Newer/enriched state kept; no duplicates (AC-048). |
| Realtime down > 30 s, tab hidden | No polling; on visible, fetch immediately then every 15 s (AC-016). |
| Typist closes the tab or leaves the conversation mid-typing | Indicator disappears ≤ 5 s (AC-017). |
| Anon, outsider, public-topic, or removed-member typing access | Refused / no events; removed member's app leaves at once; tampered client bounded by D3 (AC-019). |
| Forged mention IDs, plain "@name", changed mentions on replay, recipient removed before replay | No mention for non-members/self/plain text; changed composition → 409; unchanged replay returns the stored message (AC-024, AC-046). |
| Recipient removed or account switched after commit but before the notification is shown | No notification once the app has the removal/switch signal; a removal not yet received at the final check is the accepted D6 race (AC-049). |
| Manual retry of an expired item hits 429 or an unknown outcome | New 24 h window: retried/fenced automatically (AC-010). |
| Partial reads by others during a Realtime-only outage | Receipt summaries and open reader details update via polling (AC-016). |
| Hidden tab receives a mention event first while another tab views that conversation | No notification (AC-026). |
| Malicious, oversized, hanging, or sustained metrics traffic | Rejected or dropped; route rate-limited; messaging unaffected (AC-028, AC-029). |
| Restored conversation no longer accessible | Conversation list opens without error (AC-032). |

## 12. Security, privacy, compliance, and abuse considerations
- Outbox content lives only in the user's browser, scoped to the application user ID, fenced against account switches on the client and on the server (expected-sender check on create and fence), and deleted on confirmed explicit sign-out.
- The fence/lookup call acts only on the caller's own message for that key, never creates a message, and is rejected for anon users and for other users' keys.
- Every create request consumes a per-user request budget and fence/lookup calls their own, so the insertion-quota exemption for replays (D1) cannot be used for unlimited traffic.
- Typing topics are private and members-only for join and send (Realtime RLS with `users.supabase_uid = auth.uid()::text` → `users.id`); the app leaves within 5 s of a removal; residual receive/send exposure of tampered removed-member clients accepted (D3, D6).
- Mentions are validated and stored server-side in the message transaction; clients cannot write them directly; only members can read them; notifications are re-authorized right before emission (residual race accepted, D6).
- Notifications never leak content of conversations the user is not (or no longer) a member of.
- Metrics: closed enums, bounded numbers and sizes, server-derived version, per-user rate limit, no free text (BR-013); unauthenticated requests are rejected and produce no metric log line.
- `mark_conversation_read` membership check and `anon` revoke on `get_unread_counts` close two Phase 4 findings.
- No service-role key in client code; service-role use never replaces application authorization checks.
- Every migration, RLS/Realtime policy, repository, and API route change passes the Supabase/RLS review gate.

## 13. Accessibility, localization, and usability considerations
- UI copy in Brazilian Portuguese. The banner text, sign-out dialog text, typing phrases, and mention notification title in this SPEC are required; item-state labels ("pendente", "enviando", "expirada"), actions ("Cancelar", "Tentar de novo", "Apagar"), are proposed (the storage message in FR-033 is the owner's D5 wording), and equivalent Portuguese wording with the same meaning is accepted (D4).
- Connection banner uses a polite live region; item states have text labels, not only icons.
- Item actions and the sign-out dialog are keyboard-operable with visible focus; the dialog traps focus and Esc means Cancelar.
- The mention list follows the combobox/listbox pattern and is announced to screen readers.
- The mention highlight does not rely on color alone.
